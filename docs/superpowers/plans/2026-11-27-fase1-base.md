# CADARVIS Fase 1 (Base) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Servidor y app web base de CADARVIS: usuarios con rangos y permisos, configuración, planes, clientes con ubicación en mapa, y mapa de puntos de la red.

**Architecture:** Servidor Node.js **sin dependencias npm**: `node:http` con un router propio, `node:sqlite` (SQLite integrado), `node:crypto` (scrypt) y `node:test` para pruebas. API JSON en `/api/*` y frontend estático (HTML/JS/CSS sin framework) en `public/`. Leaflet se guarda en `public/vendor/leaflet/` con un script que lo descarga en el servidor.

**Tech Stack:** Node.js ≥ 22.13, node:sqlite, node:http, node:test, Leaflet 1.9.4 (vendored).

**Spec:** `docs/specs/2026-11-27-cadarvis-design.md` (secciones 5, 7, 8.1, 8.2 —solo planes—, 8.7, 8.8, 8.10 y 9). Esta fase es el paso 1 de la sección 11. Caja/facturación, modo sin internet, acuerdos, averías, inventario, portal y reportes van en planes posteriores.

**Desviación del spec (decisión de implementación):** el spec decía Express. Se usa `node:http` + `node:sqlite` para tener **cero dependencias**: no hace falta `npm install` en Oracle, y aquí no hay red para instalar. La API es equivalente.

## Global Constraints
- Cero dependencias npm en tiempo de ejecución. `package.json` sin `dependencies`.
- Interfaz y mensajes de error de la API en español.
- Moneda RD$, montos guardados como **enteros en centavos**.
- Zona horaria `America/Santo_Domingo`; fechas en la BD como texto ISO 8601 UTC.
- Instalación limpia: sin datos de ejemplo; el único usuario inicial es el superadmin, creado con `node scripts/crear-superadmin.js`.
- Puerto por defecto `3200` (variable `PORT`); BD en `data/cadarvis.db` (variable `DB_PATH`).
- Formato de código de cliente: `C-00001` (5 dígitos, con relleno de ceros).
- Contraseñas: scrypt con salt aleatorio de 16 bytes, formato `scrypt$<salt hex>$<hash hex>`.
- Colores: azul agua `#1E88E5`, celeste `#4FC3F7`, ocre `#D9A441`.

## Review Focus
1. **Cédula duplicada o con guiones:** `001-1234567-8` y `00112345678` son la misma cédula. Se normaliza a 11 dígitos y una repetida devuelve 409. Prueba en Task 6.
2. **Quedarse sin superadmin:** no se puede desactivar ni borrar el último superadmin activo, ni quitarle permisos al rango Superadmin. Prueba en Task 4.
3. **Coordenadas inválidas:** lat fuera de [-90, 90] o lng fuera de [-180, 180], o solo una de las dos, devuelve 400. Prueba en Tasks 6 y 7.
4. **Sesión vencida o de usuario desactivado:** devuelve 401 aunque el token exista. Prueba en Task 3.
5. **Códigos de cliente seguidos:** dos altas seguidas dan C-00001 y C-00002, nunca repetidos (se usa un contador en la tabla `counters` dentro de una transacción). Prueba en Task 6.

Esquema `001_base.sql`:

### Task 2: Router HTTP, JSON y estáticos

**Interfaces:**

Los handlers son `async (req,res,ctx)` con `ctx = {db, user?}`; un handler que retorna un valor ≠ undefined lo envía como JSON 200. `readJson(req): Promise<object>` (límite 1 MB; JSON inválido → HttpError 400 "JSON inválido"). `createApp(db): http.Server`. `startTestServer()` en helpers: BD `:memory:` migrada, servidor en puerto 0; devuelve `{url, db, close, login}`.

### Task 3: Contraseñas, sesiones, login y bitácora

**Files:** Create `src/auth/passwords.js`, `src/auth/sessions.js`, `src/auth/routes.js`, `src/auth/guard.js`, `src/audit.js`, `scripts/crear-superadmin.js`, `test/auth.test.js`

**Interfaces:**
- Produces: `hashPassword(plain): string`; `verifyPassword(plain, stored): boolean` (con `timingSafeEqual`). `createSession(db, userId): {token, expiresAt}` (token de 32 bytes aleatorios en hex; vigencia de 12 h). `getSessionUser(db, token): {id, username, full_name, role_id, role_name, perms:Set<string>} | null` (null si la sesión venció o el usuario está inactivo). `requireUser` / `requirePerm(perm)` son handlers del router que leen `Authorization: Bearer <token>` y fijan `ctx.user` (401 "Sesión inválida" / 403 "Sin permiso"). `audit(db, {userId, action, entity, entityId, before, after})`.

### Task 6: Clientes

**Files:** Create `src/clients/cedula.js`, `src/clients/routes.js`, `src/validate.js`, `test/clients.test.js`

**Interfaces:**
- `normalizeCedula(input): string|null`: quita todo lo que no sea dígito; si hay 11 dígitos los devuelve, si está vacío devuelve null, y en cualquier otro caso lanza HttpError 400 "Cédula inválida". (No se valida el dígito verificador: hay cédulas viejas que no lo cumplen. Es una decisión mía.)

- `GET /api/clientes?q=&estado=&plan_id=&limit=50&offset=0` busca en código, nombre, cédula (normalizada) y teléfono. Devuelve `{items, total}`; cada item incluye `plan_name`.
- `GET /api/clientes/:id`, `POST /api/clientes`, `PUT /api/clientes/:id` (`clientes.editar`). El código lo asigna `nextCode(db,'cliente')` dentro de `tx` usando `counters`, y se formatea `C-` + 5 dígitos.
- `GET /api/clientes/geo` → `[{id, code, full_name, status, lat, lng}]` de los que tienen ubicación (para el mapa).
- Bitácora en altas y ediciones, con el antes y el después.
